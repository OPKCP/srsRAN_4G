# Эксперимент: качество перехода абонентов между базовыми станциями (handover/failover)

**Дата создания:** 2026-09-07
**Статус:** ИДУТ ПРОБНЫЕ ПРОГОНЫ (инфраструктура и методика подтверждены; первые замеры перехода выполнены 2026-09-07)

---

## 1. Цель эксперимента

Проверить качество канала при **переходе абонентов с одной активно работающей БС на
другую** в процессе работы (поднятие второй БС + отключение первой).

Измерить просадку качества: количество потерянных пакетов, просадку скорости передачи,
паузу в передаче данных. Данные зафиксировать в отчёте. Эксперимент **циклический**:
повторить сценарий **10 раз** (10 переходов).

## 2. ⚠️ Важное терминологическое уточнение

Согласно заметке `/memories/repo/handover-blocker.md`, **классический бесшовный
меж-eNB S1-хендовер в этом форке НЕ работает end-to-end**: MME
(`srsepc/src/mme/s1ap.cc`) не обрабатывает `HandoverRequired`.

Поэтому фактически эксперимент проверяет **аварийное переключение (failover)**:
абонент теряет радиоканал с БС1 → повторная регистрация/Attach через БС2 → новая
сессия. Метрики отражают время деградации и повторного подключения, а НЕ бесшовный
перенос сессии. **В отчёте необходимо явно зафиксировать это допущение.**

*(Опция на будущее: доработать MME для реального S1-хендовера — отдельная большая
задача, потребует пересборки образа длительностью в часы.)*

## 4. Сценарий одной итерации

Исходное состояние: активна **только eNB1**, оба клиента подключены к ней, идёт
тест канала (пинг + замер скорости).

1. **Прогрев eNB2** — режим второй БС устанавливается **до этапа формирования
   излучения** (см. §6, ограничение).
2. **Включение излучения eNB2** — eNB2 начинает передавать (overlap с eNB1).
3. **Ожидание перерегистрации** — пока оба клиента не перейдут на eNB2
   (критерий по `/api/clients` + логи eNB/EPC).
4. **Отключение eNB1** — `docker stop enb` (первая БС гаснет).
5. **Фиксация просадки** — сбор метрик в окне перехода.
6. **Стабилизация** — выдержка на eNB2.
7. (для цикличности) возврат: eNB1 снова активна, eNB2 гаснет, и повтор.

## 5. Измеряемые метрики

| Метрика | Источник | Как/чем фиксируем |
|---------|----------|-------------------|
| Потери пакетов (в окне перехода) | клиент-тестер (пинг) | высокочастотный лог потерь |
| Просадка скорости | клиент-тестер (поток /api/stream) | непрерывная запись скорости |
| Пауза в передаче | клиент-тестер | время, когда поток данных остановился |
| Время «нет связи» | сервер по WS-heartbeat | gap между connected у клиента |
| Моменты включения/выключения БС | оркестратор | таймстемпы команд docker start/stop |
| На какой БС абонент | EPC-журнал / логи eNB | сопоставление Attach/RACH |

> ⚠️ Текущая история пишется **раз в 60 с** — для фиксации просадки при переходе
> (тайминги в секундах) требуется высокочастотное логирование (1–2 с) → см. задачи доработки.

## 6. Известные ограничения / открытые вопросы

1. **«Прогрев БС без излучения»** — srsenb, вероятно, начинает излучать сразу после
   старта. Возможность «тихого» режима не подтверждена. Если нет — «подъём eNB2»
   = одновременный старт излучения (пересечение). **Требует проверки.**
   *(Также: первый старт eNB после простоя занимает 3–5 мин — формирование FFT-плана;
   для цикла из 10 итераций это критично — нужен «горячий» режим eNB2.)*
2. **Нет автоматического определения «какой абонент на какой БС»** — нужен для
   критерия «переход завершён» и для сопоставления метрик одного телефона.
3. **Синхронизация времени** — клиенты/EPC/eNB-хосты на разных часах; для графиков
   сводить все события к серверному времени (10.0.0.1) или настроить NTP.
4. **Идентификация абонента при смене IP** — при повторном Attach IP может смениться;
   для связности метрик опираться на IMSI/постоянный идентификатор.

## 7. Оркестрация — ПОЛУРУЧНОЙ режим (текущий план)

- читать `/api/clients`, логи `epc`/`enb`/`enb2`;
- фиксировать моменты перехода и собирать метрики.

После первых прогонов и выявления проблем — создать **скрипт-оркестратор**
(см. задачи доработки).

## 10. Пробные прогоны (2026-09-07) — первые результаты

**Прогон A: пауза eNB1, клиенты были на eNB1 → переключение**
- Метод: сброс счётчиков потерь (команда `reset-ping`), затем `docker pause enb` (base5), T0=20:04:10.
- Хронология (по телеметрии сервера): T+6–10с offline; T+~18с WS разорваны (клиенты отвалились);
  T+~38с оба переподключились на БС **192.168.1.20** (подтверждено EPC, E-RAB на .20 в 17:04:48).
- Метрики: **потери = 38 пакетов/клиент**; время переподключения ~38с.

**Наблюдение с телефона (визуально) — согласуется с телеметрией:**
- После отключения SDR телефон ~**30 с** держал прежнее состояние сети (индикатор 4G),
  затем обнаружил отсутствие сети;
- ~**8–9 с** ушло на подключение к другой БС;
- Итого ~38–39 с — совпадает с серверными ~38с (38 потерянных пингов @1/с).

> Интерпретация времени переподключения: ~30с (таймауты RLF/радиоканала, UE «держит» старую сессию)
> + ~8–9с (реселекция/новый Attach на доступную БС). Не бесшовный хендовер — это failover с новым Attach.

**Важное замечание:** клиенты многократно переходят на **БС 192.168.1.20** (не на eNB1/.25 и не на eNB2/.26),
которая не в составе описываемой топологии (SSH не доступен, host живой). FBажно идентифицировать .20 —
она реально принимает абонентов и влияет на результаты эксперимента. (См. открытые вопросы §6.)
