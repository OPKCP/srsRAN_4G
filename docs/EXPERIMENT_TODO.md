# Задачи доработки: эксперимент «переход между БС» + устойчивость тестера

**Дата:** 2026-09-07
**Связанный треккинг:** `docs/EXPERIMENT_HANDOVER_TRACKING.md`

Разбито по областям. Приоритет: P0 (блокирует эксперимент) → P1 (важно) → P2 (желательно).

---

## A. Клиент (quality-testing/static/tester.js)

### A1. [P0] Устойчивость замера скорости к падению сети
- [ ] При разрыве сети во время загрузки `/api/stream` (ошибка fetch/чтения) тест
      **не должен** окончательно останавливаться, а переходить в состояние
      «ожидание восстановления».
- [ ] После переподключения клиента к сети (и к новому серверу/той же) — автоматически
      **возобновлять замер скорости**, не требуя ручного нажатия.
- [ ] Пока сеть недоступна — корректно отображать «нет связи / переподключение».

### A2. [P1] Динамический таймаут запроса по результатам пинга
- [ ] Таймаут пинга/запроса **подстраивать динамически**: например, удвоенное среднее
      время пинга (или `2 * avg_ping`, с нижним/верхним пределами).
- [ ] Использовать этот таймаут в пинге и (если применимо) в чтении стрима.
- [ ] Не срабатывать на обычный рост RTT при загрузке канала, но корректно ловить
      реальный обрыв.

### A3. [P2] Стабильный идентификатор абонента (не только IP)
- [ ] Для связности метрик при смене IP (повторный Attach) — добавить устойчивый
      идентификатор клиента (IMSI не виден браузеру; рассмотреть сохранение в
      localStorage/постоянный ID), чтобы сервер мог сопоставить «тот же телефон».

---

## B. Сервер (quality-testing/server/app.py)

### B1. [P0] Активный мониторинг клиентов СЕРВЕРОМ через WebSocket
- [ ] Сервер сам **пингует клиентов через WS-канал** (не через ICMP-утилиту ping):
      периодически шлёт клиенту запрос/эхо, клиент отвечает; сервер замеряет RTT и
      определяет живость канала.
- [ ] Сервер **определяет момент отключения клиента** (обрыв WS / нет ответа N раз
      подряд) и **момент переподключения** (новое WS-соединение).
- [ ] Фиксировать эти события с таймстемпом в журнале эксперимента.

### B2. [P0] Высокочастотное логирование для эксперимента
- [ ] Добавить возможность записи метрик в CSV **с частотой 1–2 с** (или по событию),
      не только раз в 60 с (текущий режим).
- [ ] В «режиме эксперимента» логировать агрегированно: потери, скорость, пауза,
      connected/disconnected события, с общими таймстемпами.

### B3. [P1] Мост для оркестратора / эксперимента
- [ ] Endpoint(ы) для управления сценарием (start/stop эксперимента, снимок состояния,
      отметка «момент перехода»).
- [ ] Отдавать сводку «клиент → на какой БС» (если станет доступно от eNB-логов).

---

## C. Оркестратор (полуручной → скрипт)

### C1. [P1] Полуручное управление (текущий этап)
- [ ] Управление контейнерами БС по командам: `docker start/stop enb` (base5),
      `docker start/stop enb2` (pi5).
- [ ] Сбор данных: `/api/clients`, логи `epc`/`enb`/`enb2`.
- [ ] Фиксация таймстемпов включения/выключения БС.

### C2. [P2] Скрипт-оркестратор (после первых прогонов)
- [ ] Создать скрипт (на ПК, где есть ssh-доступ к обеим малинкам), выполняющий
      цикл из 10 итераций автоматически:
      прогрев eNB2 → излучение → ожидание перерегистрации → отключение eNB1 →
      фиксация метрик → возврат.
- [ ] Критерий «переход завершён» по `/api/clients` + логам eNB/EPC.
- [ ] Агрегированный CSV-отчёт по итерациям.

---

## D. Прогрев БС и особенности стенда

- [ ] [P1] Проверить, возможен ли «прогрев eNB2 без излучения». Если нет — уточнить
      сценарий (overlap при подъёме). Учесть 3–5 мин холодного старта (FFT-план) —
      eNB2 должен быть «горячим» (прогретым) до начала перехода.

---

## E. Синхронизация времени / сопоставление данных

- [ ] [P1] Свести таймстемпы всех источников к серверному времени (10.0.0.1) либо
      настроить NTP на клиентах/EPC/eNB-хостах.
- [ ] [P2] Сопоставление метрик конкретного телефона при смене IP (см. A3).

---

## F. Отчётность

- [ ] [P1] Структура отчёта по эксперименту (ГОСТ-стиль, как в `docs/`), включая:
      методику, допущение о failover (не бесшовный хендовер), таблицу из 10 итераций
      (потери, просадка скорости, пауза, время перехода), выводы.
- [ ] [P2] Формирование графиков (пинг/скорость/потери vs время) из CSV.
