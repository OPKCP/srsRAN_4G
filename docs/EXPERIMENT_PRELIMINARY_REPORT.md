# Предварительный отчёт по эксперименту «Переход абонентов между базовыми станциями»

**Дата:** 2026-09-07
**Статус:** ПРЕДВАРИТЕЛЬНЫЙ (пробные прогоны; официальный отчёт в ГОСТ-стиле будет дополнен после набора статистики по 10 итерациям)
**Связанные файлы:** `docs/EXPERIMENT_HANDOVER_TRACKING.md` (треккинг), `docs/EXPERIMENT_TODO.md` (задачи)

---

## 1. Цель

Оценить качество канала при переходе абонентских устройств с одной активно работающей
базовой станции на другую в процессе работы (подъём второй БС + отключение первой).
Измерить просадку качества: количество потерянных пакетов, просадку скорости, паузу
в передаче данных. Эксперимент циклический — целевые 10 переходов.

## 2. Терминологическое допущение

Классический бесшовный меж-eNB S1-хендовер **не работает end-to-end** в используемом
форке srsRAN_4G: MME (`srsepc/src/mme/s1ap.cc`) не обрабатывает `HandoverRequired` (см.
`/memories/repo/handover-blocker.md`). Поэтому фактически измеряется **аварийное
переключение (failover)**: абонент теряет радиоканал → повторная регистрация/Attach через
другую БС → новая сессия. Метрики отражают деградацию и время повторного подключения.

## 3. Методика

1. На клиентах (браузер телефона, страница тестера) работает непрерывный пинг шлюза
   (HTTP-RTT ~1 пинг/с) и, при необходимости, тест скорости (загрузка `/api/stream`).
2. Счётчик потерянных пакетов обнуляется командой `reset-ping` непосредственно перед
   окном перехода (чистый замер).
3. Работающая БС «гасится» (`docker pause` контейнера eNB), клиенты теряют канал и
   переходят на доступную работающую БС.
4. Фиксируются: время переподключения, число потерянных пакетов, целевая БС (по логам EPC).

## 4. Инструменты (развёрнуты)

- Веб-сервер качества (`quality-testing/`): список файлов, тестер канала, WebSocket,
  определение БС клиента по логам EPC, серверный пинг клиентов (`srv-ping`), команды
  управления (reload, speed start/stop, reset-ping, page-state), отладочный канал.
- Адреса клиентов: `http://10.0.0.1:8080/`, `/tester.html`; состояние `http://192.168.1.26:8080/api/clients`.

## 5. Результаты пробных прогонов (2026-09-07)

### Прогон A: пауза eNB1 → переподключение клиентов на другую БС
- Исходно: клиенты на eNB1; счётчики потерь обнулены; T0 = 20:04:10 (пауза `enb` base5).
- Динамика (телеметрия сервера):
  - T+6–10 с — клиенты `offline` (канал eNB1 лёг);
  - T+~18 с — WS-сессии разорваны (`/api/clients` = {}), клиенты отвалились;
  - T+~38 с — оба клиента переподключились на БС **192.168.1.20** (подтверждено логом EPC: E-RAB на .20 в 17:04:48).
- Метрики: **38 потерянных пакетов на клиента**; время переподключения **~38 с**.

### Наблюдение с телефона (согласуется с телеметрией)
- ~30 с телефон держал прежнее состояние сети (индикатор 4G), затем обнаружил отсутствие сети;
- ~8–9 с — подключение к другой БС;
- Итого ~38–39 с (≈ 38 потерянных пакетов при 1 пинге/с).

**Интерпретация времени переподключения:** ~30 с (таймаут радиоканала/RLF — UE «держит» старую
сессию) + ~8–9 с (реселекция + новый Attach на доступную БС). Это не бесшовный хендовер, а
failover с повторным Attach.

### Дополнительные наблюдения
- `docker pause/unpause` eNB варианен и без потери функциональности (SDR после unpause
  восстанавливает излучение; в логах лишь нефатальный underrun).
- Клиенты не возвращаются автоматически на восстановленную БС (обратного reselection нет).
- Многократно клиенты переходят на **БС 192.168.1.20** (не в составе топологии eNB1/eNB2;
  SSH на неё недоступен, хост живой) — БС реально принимает абонентов и влияет на результаты.
  **Требуется идентификация .20 перед официальным прогоном.**

## 6. Выводы (предварительные)

1. Методика и инструменты измерения просадки работают: чистое измерение потерь на окне
   перехода через `reset-ping` + наблюдение переподключения по телеметрии и логам EPC.
2. Время переподключения ~38 с и ~38 потерянных пакетов (при 1 пинг/с) являются
   предварительной оценкой просадки для сценария аварийного переключения.
3. Для чистого эксперимента «eNB1 ↔ eNB2» требуется изолировать/идентифицировать БС
   `192.168.1.20`, иначе она перехватывает абонентов и искажает картину.

## 7. Дальнейшие шаги

- Идентифицировать БС `192.168.1.20` и решить, как учитывать/исключать её.
- Определить обновлённую схему цикла (одна доступная БС в момент времени).
- Набрать статистику по 10 итерациям; зафиксировать потери, время перехода, просадку
  скорости, паузу передачи в отчёт.
- При необходимости — высокочастотное логирование (2 с) для детализации просадки.
