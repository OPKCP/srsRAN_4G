# Исследование времени холодного старта БС (формирование FFT-плана)

**Методика:** остановка БС → удаление файла FFT-плана (`~/srsran/fftw/.srsran_fftwisdom`)
→ запуск БС → мониторинг лога docker с таймстампами (`docker logs -t`).
Момент «формирование излучения» = появление в логе записи
`Setting frequency: DL=.. МГц, UL=.. МГц`.

## Ключевые этапы старта (БС1/БС2)

1. `Using binary srsenb` — инициализация процесса.
2. `Opening 1 channels in RF device` — открытие SDR.
3. `Actually got clock rate 23.04 MHz` — настройка мастера-частоты USRP (быстро, ~5-25 с от старта).
4. **Формирование FFT-плана** — самый длительный этап (CPU-интенсивный), ~3-4 минуты,
   в этот период в stdout srsenb новых сообщений нет (процесс «молчит», активно считает).
5. `RF device 'UHD' successfully opened` → `eNodeB started` → `Setting frequency DL/UL` —
   начало излучения.

## Выводы

- **Холодный старт (с формированием FFT-плана) занимает ~3.5–4 минуты** на обеих БС.
- Различия между БС1 и БС2 незначительны (~15 с), в пределах погрешности запуска —
  время определяется мощностью CPU и одинаковым образом srsran.
- **FFT-wisdom файл в этого сборка НЕ записывается** (`~/srsran/fftw/.srsran_fftwisdom`
  и `/var/srsran` остаются пустыми после старта). То есть повторный «тёплый» старт
  в текущей конфигурации также будет тратить время на FFT. Хранение `~/srsran/fftw`
  в `/var/srsran` ускорения не даёт (план каждый раз формируется заново в памяти).
- Для ускорения будущих стартов потребуется иной механизм сохранения FFT-плана
  (пересборка/опция srsenb), либо принимать ~4 мин на каждый холодный старт БС.

## Примечания

- Healthcheck контейнера `epc` показывает "unhealthy" — штатно (healthcheck под srsenb,
  для srsepc не применим), на время остановки не влияет.
- После замера БС1 и БС2 остались в рабочем состоянии (излучают на своих частотах).
