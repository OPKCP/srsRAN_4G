# srsRAN_4G — Инфраструктура удалённого тестирования канала (quality-testing)

Превращает файловый веб-сервер ядра (`webserve`, `http://10.0.0.1:8080/`) в
инструмент тестирования качества соединения со стороны абонентских устройств
(браузеров телефонов, находящихся за NAT EPC в подсети `10.0.0.0/24`).

Модель соединения — **pull + WebSocket**: клиент сам открывает WS-канал на сервер,
сервер по этому каналу шлёт команды (перезагрузка страницы, старт/стоп теста
скорости). Никаких инициируемых сервером соединений к телефону не требуется.

## Возможности

- **`/` (index.html)** — список раздаваемых файлов + ссылка на тестер.
- **`/tester.html`** — страница тестера канала:
  - непрерывный «пинг» шлюза (HTTP-RTT) с мгновенным значением, скользящим средним
    и числом потерь за последние 100 пингов (+ мини-график);
  - загрузка бесконечного потока случайных данных с расчётом скорости (кнопки
    «Запустить/Остановить»; данные выбрасываются, не мусоря RAM/диск клиента);
  - идентификация клиента по IP, который сервер видит при загрузке (10.0.0.x).
- **`/ws`** — WebSocket: heartbeat состояния клиента + приём команд от сервера
  (`reload`, `speed start/stop`).
- **`/api/clients`** — JSON-состояние всех подключённых клиентов (для нас/дашборда).
- **`/api/clients/<ip>/cmd`** — отправка команды конкретному клиенту.
- **`/api/reload-all`** — перезагрузка всех клиентов (обновление кода).
- **`/api/stream`** — бесконечный поток случайных данных для замера скорости.
- **История (CSV)** — журнал замеров по датам в `HISTORY_DIR` для отслеживания
  изменения характеристик при перемещении клиентов.

## Доставка обновлённого кода клиентам

После правки `static/tester.js` (или `tester.html`, `tester.css`):

1. Файлы раздаются с `Cache-Control: no-store`, поэтому после reload браузер
   затянет свежую версию.
2. Разослать перезагрузку всем клиентам:
   ```
   ./qctl.sh reload-all
   ```
   (или конкретному: `./qctl.sh reload 10.0.0.14`)

## Каталоги / файлы

```
quality-testing/
├── server/app.py            # сервер (Flask + flask-sock, WS)
├── server/__init__.py       # (пакет; может отсутствовать)
├── static/tester.html       # страница тестера (IP подставляется сервером)
├── static/tester.js         # клиентский код (vanilla JS)
├── static/tester.css        # стили
├── requirements.txt         # flask, flask-sock
├── Dockerfile               # python:3.12-slim
├── run_webserver_quality.sh # запуск контейнера на pi5 (в namespace epc)
└── qctl.sh                  # консольное управление клиентами + просмотр истории
```

## Запуск на стенде (pi5)

Перенести каталог `quality-testing/` на pi5 (например, в `~/srsran/quality-testing`)
и запустить:

```bash
~/srsran/quality-testing/run_webserver_quality.sh
```

Скрипт соберёт образ, запустит контейнер `webserve` в namespace EPC и выведет
адреса. После этого на телефонах открыть `http://10.0.0.1:8080/`.

## Что переиспользовано / решения

- Файловый сервер переписан (вместо `python3 -m http.server`): сохранён в
  репозиторий, добавлены WS, стрим, API, история.
- Минимум зависимостей: `flask` + `flask-sock`; клиент — чистый vanilla JS.
- «Пинг шлюза» — HTTP-RTT до самого веб-сервера (`10.0.0.1:8080`), т.к. браузер
  не может слать ICMP. Это меряет латентность до SGi-шлюза ядра.

## Управление с ПК

С ПК-посредника (или с pi5) доступ к API — по внешнему IP pi5 `192.168.1.26:8080`:

```bash
QCTL_BASE=http://192.168.1.26:8080 ./qctl.sh clients
QCTL_BASE=http://192.168.1.26:8080 ./qctl.sh reload-all
```
